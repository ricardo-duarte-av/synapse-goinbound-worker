# Grafana dashboard

`goinbound-worker.json`. Import it via **Dashboards → New → Import**. Any
Prometheus data source works through the `datasource` variable, so no UID needs
editing.

Prometheus must scrape the worker first. Add this beside `gopro-worker` in
`/opt/stats/prometheus/prometheus.yaml`:

```yaml
  - job_name: goinbound-worker
    static_configs:
      - targets: ["av-goinbound-worker-1:9200"]
```

## Variables

| Variable | Meaning |
|---|---|
| Bucket | Range window for every `rate()` and quantile. Prometheus scrapes every 15s, so 30s is the floor. The default is 5m. |
| Job | The goinbound job(s). |
| Synapse server_name | Filters Synapse's own metrics. The `inbound-federation` job also scrapes `matrixbridg.es`. |
| Python inbound job | The Python worker's job, for the comparison panels. |

## Rows

| Row | What it shows |
|---|---|
| Overview | Transactions per second; the share answered natively, or that would be in shadow mode; and disagreements, forward failures and upstream errors in the window. |
| Routing | Every transaction by route and reason, and latency by route. |
| EDUs | EDUs by type and action, forwards by destination writer, forward latency, outcomes and retries. |
| Shadow evaluation | What native mode would have done, and disagreements with Synapse. |
| Write mode decisions | The decide check (write mode's decision against what Synapse did), its deferrals by reason, the policy server checks, and v2.1 set-order ties. |
| Write mode | Only with modes.pdu canary or native: events by outcome, write latency, persister calls, device resyncs, queue pruning, origins marked as up. |
| Handing back to Synapse | What still needs a Synapse process: staged events and the oldest one's age (all, and in rooms no process holds), the plan shadow's reasons, events deferred or given up, sweep nudges. |
| Synapse, for comparison | Synapse's own fed_send_edu counts per writer, which must not change across the move to native. The Python worker's /send rate, which should fall by ~96%. |
| Database | Each named query's rate and latency, and ACL lookups by source. |
| Process | CPU, memory and goroutines, beside the Python inbound worker's. |

## Alert rules

Grafana-managed rules on the Prometheus data source (**Alerting → Alert rules →
New alert rule**). Neither is in the dashboard JSON.

| Rule | Query | Condition | Evaluate | Summary |
|---|---|---|---|---|
| Staged inbound event unattended | `max(goinbound_staging_unattended_oldest_seconds{job="goinbound-worker"}) or vector(0)` | above 300 | every 1m, pending 5m | A staged inbound event has waited over 5 minutes in a room no process holds: nobody is going to process it. |
| Write mode gave up on an event | `sum(increase(goinbound_write_events_total{job="goinbound-worker", outcome="given_up"}[15m])) or vector(0)` | above 0 | every 1m, pending 0 | Write mode dropped an event it could not handle (write.fallback: none). The ERROR log line names it. |

The first is the one that matters with `write.fallback: synapse`. The gauge is set
at each minute's sweep and covers every staged event, Synapse's too, but only in
rooms whose inbound lock is free or dead (not renewed for 2 minutes, Synapse's
`_LOCK_TIMEOUT`). Do not alert on `goinbound_staging_oldest_seconds`: a process
working through Matrix HQ's missing prevs keeps an event staged for many minutes
(over 8 on 2026-10-16) while it holds the lock. If it fires, a room's head event
is waiting for a Synapse process that is not sweeping, most likely main once it
is the only upstream. Check `goinbound_sweep_nudges_total`,
and find the room in the worker's log, or with:

```sql
SELECT room_id, origin, event_id, to_timestamp(received_ts / 1000)
FROM federation_inbound_events_staging ORDER BY received_ts LIMIT 10;
```

The second only applies with `write.fallback: none`. goinbound's series carry
`job` and `deployment`, not Synapse's `server_name`: filter on `job`. Both
queries end in `or vector(0)` because the series exist only while write mode is
on, and `given_up` only once an event has been given up; without it the rule
has no data, which Grafana alerts on by default (it did, 2026-10-16). Set **No
data** to OK as well. A worker that is down is a matter for an `up` alert, not
these.

The JSON is generated by `tools/gen_dashboard.py`. Edit that file and
regenerate, rather than editing the JSON by hand:

```sh
python3 tools/gen_dashboard.py deploy/grafana/goinbound-worker.json
```
